# LLM + 固定模板的根因解释机制：现状核查与改造方案（v1）

- 日期：2026-11-11
- 状态：**仅方案，未实施**。本文不改任何代码、不重跑实验、不修改 `output/runs/` 下任何产物。
- 依据 run：`v23-20261111T022417`（正式档，`n_bootstrap=100`，9 模板 + 3 类级 + 1 全局）
- 目标口径（用户原话归纳）：**图算出来 Top-5 → 交给 LLM 判断这几个根因合不合理 → 按固定模板解释**；解释同时受三重约束——图本身（只准用给定的边与系数）、排序结果（不准自己重排）、实际物理知识（知识库里已有的机理条目）。

---

## 0. 结论先行

**现机制最大的一个缺陷：9 份模板级解释从来没有把 Top-5 交给 LLM 判断过。** 由于 `V23-DESIGN-020` 的"LLM 降频铁律"，模板级解释被固定成离线规则文本（本次 run 实测 13/13 份 `requested_backend="rule"`、`backend="rule"`），LLM 即使被调用，也只拿到"计数 + Top5 的度数和总效应"，**拿不到 59 条稳定边及其系数、拿不到每个候选的入/出边、拿不到知识条目正文与 id**；提示词也只有"复述七章结构"，既没有"判断合理性"的任务，也没有可被程序校验的输出 schema。

一句话：现在是「规则模板在复述图统计」，不是「LLM 在受约束地判断 Top-5」。

## 1. 现状核查（全部为实测，不是推测）

### 1.1 13 份解释文件的真实后端

`Code/output/runs/v23-20261111T022417/reports/llm_explanation_*.json`：

| 文件 | 级别 | `requested_backend` | `backend` | `degraded` | `cache_hit` |
|---|---|---|---|---|---|
| `llm_explanation_{LOCA,SGATR,FLB}_{low,mid,high}.json`（9 份） | 模板级 | `rule` | `rule` | `false` | 字段不存在 |
| `llm_explanation_class_{LOCA,SGATR,FLB}.json`（3 份） | 类级 | `rule` | `rule` | `false` | `false` |
| `llm_explanation_global.json`（1 份） | 全局 | `rule` | `rule` | `false` | `false` |

- **连"请求 LLM"都没发生过**（`requested_backend` 就是 `rule`），不是"请求了但失败降级"。
- 所以不存在"降级"、也不存在"LLM 判断"；13 份全部是 `render_rule_explanation()` 产出的离线文本。
- 文件里也没有 `explanation_mode` 字段（实测 `mode=None`），外部无法一眼区分"规则稿"和"模型判定稿"——**可核查性缺口**。

### 1.2 代码里两套链路并存，v2.3 链路实际被关掉

| | v2.1 旧链路 | v2.3 现链路 |
|---|---|---|
| key 读取 | `_get_api_key()`：先进程环境 `DEEPSEEK_API_KEY`，再 `Code/.env` / 仓库根 `.env` | `_call_chat_completions()`：只读进程环境 `CAUSALTRACE_LLM_API_KEY` |
| 端点 | `config/paths.py` 的 `LLM_BASE_URL = https://api.deepseek.com` + `/v1/chat/completions` | 只读进程环境 `CAUSALTRACE_LLM_BASE_URL` |
| 启用判定 | 有 key 即可 | `llm_unavailable_reason()`：两个变量**必须同时存在**，否则返回"不可用" |
| 提示构造 | `_build_prompt_context(rec)`：chain 记录 E1/E2/E3、A(x)、RRF 传播链 | `_build_v23_prompt(payload)`：整段 payload JSON + 七个章节标题 |
| 校验 | `check_faithfulness()`：变量名合法集合 + RRF 数值对拍 | `verify_faithfulness()`：数字须在 payload（2 位小数）+ 大写变量名须在词表 |

**关键事实：两套链路的 key 变量名不同。** `Code/.env` 里只有 `DEEPSEEK_API_KEY`（v2.1 认它），而 v2.3 只认 `CAUSALTRACE_LLM_*`（无人设置）。所以即使保留下面的降频铁律，v2.3 的 llm 后端在环境层面也永远"不可用"。

### 1.3 降频铁律（缺陷的直接来源）

`llm_explanation.py` 第 1015–1025 行的 `V23-DESIGN-020` 注释原文：

1. 模板级 9 份解释**一律 rule 后端，不再逐模板调用 LLM**；
2. LLM 只用于 3 份类级汇总 + 1 份全局结论；
3. 汇总解释须引用模板 id 与数字，忠实性校验查"数字/变量名/模板 id"三项；
4. 同 `run_id` + 输入 sha256 命中即复用。

即：**用户想要的"逐模板让 LLM 判断 Top5"，恰好被这条铁律排除在外。**

### 1.4 现在到底喂了什么（以 `LOCA_low` 实测为例）

payload 共 32 个键。有效信息只有：

- `root_candidates`：5 条，每条 11 个字段
  `rank / variable / subsystem / role / total_effect / in_degree / out_degree / reach_size / weighted_reach / auxiliary_cL / auxiliary_piL`
- `variables`：15 个变量**代码**（无中文含义、无单位）
- `k2`：只有 `relation_id + status`（本次 `R1_inventory_leak / R3_eci_trigger`，均 `not_violated`）
- `k3`：只有统计量（`coverage=0.4`、`n_reverse_edges=2`、`n_missing=1`）与两条反向边、一条缺边
- 其余：门控比例、截断阈值、`cond(I−B)`、偏离度分档计数、6 条 limitations

**缺失（逐项核对 `payload` 键与内容）**：

| 缺什么 | 实证 | 为什么这是硬伤 |
|---|---|---|
| 稳定边表（本次 59 条）与系数 | `payload_keys` 中没有 `stable_edges`，只有 `n_stable_edges=59` 这个计数 | LLM 无法验证 `in_degree=4 / out_degree=7` 从哪来，也无法判断边方向是否物理合理 |
| 每个候选的入边/出边清单 | `root_candidates[i]` 只有度数，没有边 | "这条边系数是多少、稳不稳"全部不可查 |
| 边的不确定性 | `weight_iqr`、`dir_e`、`f_e`、`count` 全在 signature 里，未进 payload | 无法区分"方向 100% 一致"与"50% 一致" |
| 变量字典 | `variable_dictionary.yaml` 有 96 个变量的 `subsystem/meaning/unit`，payload 里只有代码 | 模型只能靠自身先验猜 `RHMT` 是什么，等于放开了"编故事"的口子 |
| 知识条目正文 | K2 只有 id+status，缺 `lhs/rhs/expected_sign/missing_terms`；K3 缺 `expected_chain` 与逐边比对明细 | 无法要求模型"引用条目 id 并说明依据" |
| 冲突项结构化 | `reverse_edges` 埋在 `k3` 里，K2 与图证据之间没有交叉冲突表 | 模型看不到"哪里自相矛盾"，自然也不会标注冲突 |

### 1.5 提示词与校验的缺口

- `_build_v23_prompt()` 全文只做两件事：贴 JSON、列七个章节标题（结论 / 证据链 / 跨组一致性 / K2 / K3 / 偏离度 / 局限）。**没有判定任务、没有"不得重排"、没有"知识引用须给 id"、没有输出 schema。**
- `verify_faithfulness()` 只查两件事：数字能否在 payload 里找到（2 位小数）、大写变量名是否在词表。
- **最要命的一处**：`generate_explanation()` 在 llm 输出不忠实时（第 998–1004 行）只 `logger.warning`，**照样以 `degraded=False` 落盘**。也就是说，即使将来真调了模型，"编了数"的文本也会被当成合格产物，只是日志里有一行警告。

### 1.6 密钥：存在、且可用

| 项 | 结论 |
|---|---|
| `Code/.env` | 存在；键名 `DEEPSEEK_API_KEY`，**非空**（长度 35） |
| 仓库根 `.env` | 不存在 |
| 进程环境 `DEEPSEEK_API_KEY` | 未设置 |
| 进程环境 `CAUSALTRACE_LLM_BASE_URL` / `CAUSALTRACE_LLM_API_KEY` | **均未设置**（v2.3 后端因此判定"不可用"） |
| 冒烟调用（至多一次，最小规模） | `POST https://api.deepseek.com/v1/chat/completions`，`max_tokens=8` → **HTTP 200**，`model_echo=deepseek-flash`，回复 2 字 |

- 本次核查**未回显密钥任何片段、未写入任何文件或日志、未入库**；只读取键名与"是否非空"。
- 结论：**key 可用，但现有 v2.3 代码路径没把它接进来**（变量名对不上，读取逻辑也不同）。改造时第一件事就是把这个接线问题定死（见 §9 决策点）。

## 2. 目标机制（一句话版本）

> 算法给出排序与 Top-5，**LLM 不改排序、不引入新变量、不新造数值**，只做三件事：逐项判定「这 5 个根因在图上和知识上说得通吗」、给出被引用的依据、把"说不通/没依据"的地方显式标出来。

输出分两层：

1. **判定层**（机器可校验，JSON）：逐候选 `verdict + 依据引用 + 一句话机理 + 冲突`；
2. **叙述层**（人可读，模板渲染）：由判定层**确定性渲染**成固定章节文本，措辞模板固定，不再让模型自由发挥。

这样"固定解释模板"落在渲染器里，"判断合理性"落在 LLM 里，"不许乱说"落在校验器里。

## 3. 证据包（evidence_pack）设计

### 3.1 顶层字段

| 字段 | 内容 | 数据来源 | 作用 |
|---|---|---|---|
| `schema` | `causaltrace/explanation_evidence/v1` | 新增常量 | 版本锚 |
| `run_id` / `template_id` | `v23-.../ LOCA_low` | manifest / 报告名 | 溯源与缓存键 |
| `accident` | `code, name_cn, group, k3_template_id` | `fault_templates.yaml` | 让模型知道事故类型与工况档 |
| `algorithm` | `engine, n_bootstrap, top_k, rank_key, gate_ratio, n_variables` | payload | 明确"排序是算法给的" |
| `nodes[]` | `variable, meaning_cn, unit, subsystem, role, in_graph` | `variable_dictionary.yaml` + payload | 禁止模型靠先验猜变量含义 |
| `stable_edges[]` | `from, to, weight_median, weight_iqr, dir_e, f_e, count` | `signature_{c}_{g}.json#stable_edges` | **三重约束之一：图证据全表** |
| `candidates[]` | `rank, variable, total_effect, in_degree, out_degree, reach_size, weighted_reach, incoming[], outgoing[]` | payload + 边表反查 | 让模型能自证度数 |
| `knowledge.k2[]` | `id, name, lhs, rhs, rhs_operator, expected_sign, status, missing_terms, applicable_accidents` | `physics_relations.yaml` + signature `auxiliary.k2` | **三重约束之三：物理知识** |
| `knowledge.k3` | `template_id, verification, expected_chain, expected_sign_direction, matched_edges[], reverse_edges[], missing_edges[]` | `fault_templates.yaml` + signature `auxiliary.k3` | 机理链覆盖 |
| `knowledge.notes` | K2/K3 的解释边界原文（"满足约束≠方向证明"） | 两个 yaml 的 `note` | 防止模型把"未违反"读成"支持" |
| `conflicts[]` | `type`（`reverse_edge`/`missing_edge`/`k2_vs_graph`/`no_knowledge_coverage`）、`subject`、`detail` | 程序预计算 | 把矛盾摊在桌面上，而不是让模型"圆回来" |
| `provenance` | `files[]` + 每文件 `sha256` | 已在 manifest 中的同类机制 | 证据包可复核 |

### 3.3 裁剪原则

1. **稳定边全表照传**（本次 59 条，单模板约 8–9 KB）：裁掉就等于裁掉了"图证据"，LLM 只能对着度数编故事。
2. **节点只传入模 15 个变量的字典条目**，不传 96 个全集（省 token，也防止模型把未入模变量当候选）。
3. **知识只传适用本事故类的条目**（LOCA → `R1`、`R3`、`K3:LOCA`），不传全部 5 条 K2 + 12 个模板。
4. **不传 `T=(I−B)⁻¹` 矩阵**：只传已算好的 `total_effect`，从源头上断掉"模型自己重算排序"的可能。
5. `conflicts[]` 由程序预计算后传入，不让模型自己去对齐三份材料。

## 4. 提示词约束

### 4.1 system（约束条款，逐条可落到校验器上）

```text
你是核电事故根因分析的审阅者，不是分析者。你的唯一任务：对算法已经给出的 Top-5 根因逐项判断"是否合理"，并给出受约束的解释。

硬约束：
1. 排序由算法给定。不得新增、删除、替换候选；不得改变名次；正文中不得暗示另一种排序。
2. 只能使用 evidence_pack 中出现的变量名、稳定边及其系数。禁止引入图中不存在的变量、边或数值。
3. 每条机理陈述必须引用 evidence_pack.knowledge 中的条目 id（K2 形如 R1_inventory_leak；K3 形如 K3:LOCA）；没有条目支撑时必须判 undetermined，不得编造因果故事。
4. K2 的 not_violated 只表示"未被否定"，不能当作"支持"；K3 只有 matched_edges 里的边才能当作支持依据。
5. 数值只允许原样引用 evidence_pack 中出现的数并保留原精度；禁止做四则运算推导新数值，禁止给出概率、置信度、百分比估计。
6. 三类证据必须分开写：图证据（边/系数/入出度）、知识证据（条目 id）、缺失证据（无覆盖）。三者冲突时必须写进 conflicts，不得用文字抹平。
7. 不确定就判 undetermined，并在 uncertainty 中写明"缺哪一条证据"；禁止用"可能/或许/通常"替代缺失依据。
8. 只输出一个 JSON 对象，严格符合给定了的 schema；不要任何解释性前后文。
```

### 4.2 user（模板骨架）

```text
以下为 CausalTrace v2.3 在 run_id=v23-20261111T022417、template=LOCA_low 上的证据包（只读产物，未重算因果）。
请逐项判定 candidates 中 5 个候选的合理性，并严格按 schema 输出 JSON。

【输出 schema】
<贴 §5 的 JSON schema>

【证据包】
<贴 §3 的 evidence_pack JSON>
```

### 4.3 明确的禁止清单（写进提示词，也写进校验器）

- 禁止重排 / 改 rank / 增删候选
- 禁止出现证据包之外的变量名（包括中文别名，如把 `RHMT` 写成"反应性温度系数"当作变量）
- 禁止出现证据包之外的数值（含自算的差值、比值、百分比）
- 禁止无 id 的"物理常识"陈述（"稳压器水位下降会导致一回路压力下降"这类，必须挂 `R1`/`R3` 或 K3 的链）
- 禁止把 K2 的 `not_violated` 写成"支持/验证"
- 禁止输出排序建议（"建议将 X 提前"）

## 5. 输出 schema（判定层）

```json
{
  "schema": "causaltrace/explanation_verdict/v1",
  "run_id": "v23-20261111T022417",
  "template_id": "LOCA_low",
  "ranking_source": "algorithm",
  "verdicts": [
    {
      "rank": 1,
      "variable": "RHMT",
      "verdict": "undetermined",
      "graph_basis": ["RHMT->TAVG", "RHMT->WHPI", "RHMT->VOL", "LVPZ->RHMT"],
      "knowledge_basis": [],
      "mechanism": "在给定图中 RHMT 总效应最高、出边 7 条，但 K2 与 K3 均未覆盖该变量，缺少可引用的机理条目。",
      "conflicts": ["no_knowledge_coverage: RHMT 无 K2/K3 条目"]
    }
  ],
  "conflict_notes": [
    "K3 期望边 VOL->P 与稳定边 P->VOL 方向相反",
    "K3 期望边 WLR->VOL 无稳定边（no_stable_edge）"
  ],
  "uncertainty_notes": [
    "链首段（WLR->VOL）缺图证据，触发变量与首段传导无法互相印证"
  ]
}
```

字段说明：

| 字段 | 取值 | 规则 |
|---|---|---|
| `verdicts[].rank` | 整数 1–5 | **必须与算法 rank 完全一致**，只做校验用，不参与渲染排序 |
| `verdicts[].variable` | 证据包候选变量名 | 必须 ∈ `candidates[].variable`，且 5 条不重复 |
| `verdict` | `supported` / `partially_supported` / `unsupported` / `undetermined` | 四态，不允许自由文本 |
| `graph_basis` | `"FROM->TO"` 字符串数组 | 每条必须是 `stable_edges` 里存在的边 |
| `knowledge_basis` | 知识条目 id 数组 | 每个必须是 `knowledge.k2[].id` 或 `K3:<CODE>` |
| `mechanism` | 一句话，≤ 60 字 | 出现的数字与变量名同样受校验 |
| `conflicts` | 字符串数组 | `unsupported` **必须**至少 1 条 |
| `conflict_notes` / `uncertainty_notes` | 字符串数组 | 可为空，但为空的 `undetermined` 会被校验器打回 |

### 判定口径（消除随意性）

| verdict | 判定条件（AND） |
|---|---|
| `supported` | K3 `matched_edges` 覆盖该变量所在链段且方向一致；图上该变量度数/总效应与之不冲突 |
| `partially_supported` | 图证据充分（有入/出边且 `dir_e` 高），但知识侧只有 K2 `not_violated`，或 K3 仅部分覆盖 |
| `unsupported` | 知识条目覆盖该变量，且图证据与之方向相反、无法用同一条目解释 |
| `undetermined` | 无任何 K2/K3 条目覆盖，或证据互相矛盾到无法取舍（此时必须写 `uncertainty_notes`） |

> 注意：`unsupported` 的语义是"**作为根因**不被支持"，不是"该变量无效/无关"。渲染时按此措辞。

**汇总统计不进 LLM 输出**（`n_supported` 等由程序算），避免"模型自造的计数"污染数值校验。

## 6. 程序侧校验

在模型返回后、落盘前执行，任一条不过即进入 §7 流程。

| # | 检查项 | 判定方法 | 不通过处理 |
|---|---|---|---|
| 1 | JSON 可解析 + schema 必填字段齐全 | `json.loads` + 必填键集合 | 立即回喂错误，重试 1 次 |
| 2 | 候选集合完全一致 | `set(verdicts.variable) == set(candidates.variable)`，长度 5，无重复 | 同上 |
| 3 | **未重排** | 对每个变量 `verdict.rank` 必须等于算法 rank；另检正文中"第 X 名"与变量映射 | 同上（重排属硬违规，直接判失败） |
| 4 | 变量名不越界 | 扫描全部文本字段的大写 token，须 ∈ `nodes[].variable` | 同上 |
| 5 | 图引用可查 | 每条 `graph_basis` 拆 `FROM->TO`，须命中 `stable_edges` | 同上 |
| 6 | 知识引用可查 | 每个 `knowledge_basis` ∈ `knowledge.k2[].id` ∪ `{"K3:<CODE>"}` | 同上 |
| 7 | 数值不越界 | 扫描全部文本字段的数字，须在证据包数值集合内（2 位小数容差，复用现有 `verify_faithfulness` 的比对方式） | 同上 |
| 8 | 枚举合法 + 冲突完整 | `verdict` ∈ 四态；`unsupported` 的 `conflicts` 非空；`undetermined` 的 `uncertainty_notes` 非空 | 同上 |

**重试策略**：第 1 次失败时，把"校验错误清单"原样回喂，允许**一次**修复调用（`temperature=0`，证据包不变）；第 2 次仍失败 → 降级。

**升级为硬失败**（不重试、直接降级）：第 3 条（重排）与第 4 条（越界变量）——这两条说明模型没有遵守"图/排序"约束，再试也是浪费。

## 7. 降级路径

| 触发 | 产物 | 报告呈现 |
|---|---|---|
| 无 key / `llm_unavailable_reason()` 非空 | `explanation_mode="rule_fallback"` | 章节标题后缀 `（离线规则稿，未经模型判断）` |
| 超时（单次 30 s）/ HTTP 非 200 / 网络异常 | 同上 + `degraded_reason` | 同上 |
| 校验两次不过 | 同上 + `validation.errors[]` | 同上，另附"校验失败项"小节 |
| 通过 | `explanation_mode="llm_verified"` | 正常渲染 |
| 通过但有 `unsupported`/`undetermined` | 仍是 `llm_verified`，另出"未获支持项"小节 | 正常渲染 + 显式列出 |

规则：

1. `explanation_mode` 三态**必填**（`llm_verified` / `llm_unverified` / `rule_fallback`），当前 `mode=None` 的状态必须消灭。
2. 兜底文本一律用现有 `render_rule_explanation()`，**不新写第二套规则模板**。
3. 单模板降级不影响其它模板；类级/全局汇总只陈述 `llm_verified` 的模板，其余逐个标 `rule_fallback`，不得混算。
4. 降级时**必须**在 `degraded_reason` 里写清是"环境缺失 / 调用失败 / 校验失败"哪一类，并把 `validation.errors` 一并落盘——便于事后分辨"没 key"和"模型不听话"。

## 8. 调用次数与缓存

| 场景 | 调用次数 |
|---|---|
| 一轮全链（9 模板级） | 9 次 |
| 含最多 1 次修复 | 上限 18 次 |
| 类级 3 份 + 全局 1 份 | **0 次**：改由 9 份 verdict 确定性汇总（避免模型再"重排"一遍） |

缓存键：

```text
cache_key = sha256( run_id + "|" + template_id + "|" + evidence_pack_sha256 )
evidence_pack_sha256 = sha256( canonical_json(evidence_pack) )
canonical_json = json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

- 现成字段 `input_sha256` 可直接复用（类级已在用），不必新增机制。
- **模板 id 必须进键**：现有实现靠 payload 内含 `template` 隐式区分，一旦 payload 结构微调就会串模板；显式进键更稳。
- 证据包内容不变（同 run、同口径、同知识库）→ 重跑报告步骤 **0 次调用**；知识库 yaml 或 bootstrap 档位一改，sha 变化 → 自动失效，不会拿旧判定冒充新结果。
- 成本量级：单模板证据包约 7–9 KB（≈3–4 k tokens），输出约 1.2 k tokens；一轮 9 次。**本文不写死单价**（以实际计费为准），量级上属于可忽略范围。

## 10. 本方案的边界

- **不改代码、不重跑、不动产物**：本文所有数字来自既有 run 的只读产物。
- 实施时需要新增/改动的位置（供后续裁决，不代表现在做）：
  1. `build_payload` → 新增 `build_evidence_pack`（补边表/字典/知识正文/冲突）；
  2. 提示词与 schema、`validate_verdict()`（§6 的 8 条）；
  3. 渲染器：由 verdict 确定性生成固定章节文本，替代目前"LLM 自由写七章"；
  4. 类级/全局汇总改为 verdict 汇总，不再单独调模型；
  5. `V23-DESIGN-020`（模板级一律 rule）**必须被新决定项 supersede**，并在台账留痕——这是口径变更，不能悄悄改。
- 一个待裁决的接线问题：v2.3 后端读 `CAUSALTRACE_LLM_*`，而现有密钥是 `Code/.env` 的 `DEEPSEEK_API_KEY`。两条路：**(a)** 读取逻辑支持回落到 `Code/.env` 的 `DEEPSEEK_API_KEY`（少配一个变量，但两套命名并存）；**(b)** 新增 `CAUSALTRACE_LLM_*` 并废弃旧读取（干净，但需改 `.env`）。本方案不预设结论。

## 11. 一句话回执

**现机制最大的缺陷：模板级 9 份解释被 `V23-DESIGN-020` 降频成纯离线规则文本（本次 13/13 份 `backend=rule`、`requested_backend=rule`），LLM 从未参与 Top-5 合理性判断；即便调用，证据包里也没有稳定边系数、每个候选的入/出边、变量含义与知识条目 id，提示词也没有判定任务和可校验的 JSON schema。**
