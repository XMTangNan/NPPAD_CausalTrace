# issues/：问题取证与审查文档

本目录只放**"记录问题"的文档**，不放交付物与方案。

## 放什么

- 指标 / 口径可靠性的审查与取证（例：`指标可靠性审查-<run_id>-<日期>.md`）
- 对某一 run 的定向体检、量级核查、方向核对（例：`方向体检-前五角色-行列和-<run_id>-<日期>.md`）
- 暴露缺陷、复现异常、对比"声明值与实测值"的核查记录

判断标准：**文档的主要用途是"证明某处有问题或记录问题"，而不是"给外部读者讲方案/交付结果"**。

## 入库纪律（2026-11-11 起执行）

**取证类文档必须入库（git 跟踪），不得只留未跟踪文件。** 动因：`量级核查` 曾只存在于工作区、
从未入库，被其它会话清理后短暂丢失，需从外部副本恢复。此后：

1. 新写的取证/审查文档，完成即 `git add`，不得长期停留在 `??` 状态；
2. 引用某 run 的取证文档，必须能从仓库本身取回（不依赖会话目录或临时路径）；
3. 若确需临时脚本，放 `Code/experiments/`（已被 gitignore），且**不得承载结论性证据**；
   一旦某脚本的产出被报告或台账引用，产出必须转存到 `issues/` 或 `output/runs/` 并入库。

## 不放什么

- 方案文档与对外呈现版（在 `方案/`）
- 对比稿、LLM 解释机制方案、机理一致性评审表草案（在 `submit/`）
- 产物入口页、报告原文、结果列表（在 `submit/` 或 `output/runs/`）
- 台账本身（唯一台账是 `Code/error_tracking.md`，本目录文档只引用其编号）

## 命名规则

`<主题>-<run_id 或日期>.md`，例如：

- `指标可靠性审查-v23-20261111T022417-2026-11-11.md`
- `方向体检-前五角色-行列和-v23-20261111T022417-2026-11-11.md`

要求：
1. 首行写明"本文是取证/问题记录，不是结果"，避免被当作成绩单引用；
2. 涉及具体 run 的，run_id 必须出现在文件名里；
3. 结论与处置状态以 `Code/error_tracking.md` 的编号为准，本目录只保存证据原文；
4. 历史文档迁入后**不改内容**，只改引用路径。
